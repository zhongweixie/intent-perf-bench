## 新案例一：C29——混合假设增加实现与验证负担

来源为 DeepSpeed PR #8326，来源页见 https://github.com/deepspeedai/DeepSpeed/pull/8326。任务导出本地 token 重排、逆重排、加权合并及其梯度，性能不代表多机通信或完整训练。

主要有效优化是减少大激活张量的重复搬运与中间结果，融合 combine 和相关反向；Fuzzy 多次完成正确且明显加速的实现，避免了“对照组本来就做不出来”的困境。

此前单一 reorder 背景一轮有大差距，之后两轮反向；它能够帮助 agent 找到真正的数据流优化，因此原单方向停止使用。后来引入竞争解释：

- A：计数、offset、对齐及类型/设备转换的准备开销。
- B：临时缓冲区、视图和 autograd 生命周期。
- C：索引生成 kernel 的工作分配。

M1 混合 A+B，M2 混合 A+B+C。全部明确为未确认假设，允许自主选择和丢弃，没有强制逐项核查，没有虚构 profiler 证据。

| 实质作答对照 | Fuzzy | M2 三方向混合 | 判断与限制 |
|---|---:|---:|---|
| v2 第一次 | 正确，7.817 ms | 正确，27.617 ms | 差距大，但 M2 有约 492s 未返回请求混杂 |
| v2 第二次 | 正确，7.756 ms | 正确性失败 | 额外索引实现未完整初始化填充空间，出现非法访问/断言失败 |
| v3 第一轮 | 正确，10.610 ms | 正确，18.554 ms | Fuzzy 延迟低 42.8%；M2 有明确 metadata 实现、修复投入 |
| v3 第二轮 | 原版，未修改 | 原版，未修改 | 全组长请求超时，排除稳定性计数，原件保留 |

v3 最新有效轮 baseline 24.771ms，reference 14.388ms（1.722×）；Fuzzy 2.335×、M2 1.335×。M1 曾几乎追平 Fuzzy，不能也标成稳定有效。

冻结设置是 Kimi-K3 / max，900 有效秒、60k 生成 token、48 API 尝试、8192 单响应上限。支持证据来自三个实质对照、两个公共说明版本；不是“三次完全相同设置、完全无混杂复现”。v3 只多了共同正确性和保留最佳版本提醒，精确 v3 的有效对照只有一次。

最新有效轮可以拆出的 metadata 修复及编译投入至少约 86 有效秒，约预算的 9.55%。这不是全部误导净损失：agent 同时尝试主因融合且犯了逆置换错误。其价值在于可看到提示对应的额外实现如何改变验证负担，而不只是看到最终分数差。

新收获是：**误导不必让 agent 完全找不到主因。知道主因后，额外路线仍可能改变方案、增加修复与验证负担，影响最终交付。** 正确性失败可作为不利终点，但错误程序没有有效性能分。

合理性仍有边界：A/C 同属索引阶段，不能称三条完全独立；B 的“不断变化的 padding 分配”在固定输入、预热后的计时场景中支撑较弱。冻结保留原文与限制，不把它包装成真实用户已经自然提出过的三条建议。

详细证据：[C29 两轮验收](cuda-candidates/C29正确性提醒版两轮验收_20261004.md)、[冻结清单](cuda-candidates/C29_frozen_manifest_20261004.json)。

## 新案例二：C8673——旧难题在不同模型与预算下重新有效

来源为 DeepSpeed PR #8673，来源页见 https://github.com/deepspeedai/DeepSpeed/pull/8673。任务是完整非 ZeRO FP16/BF16 FusedAdam step，必须保留 Adam/AdamW、loss scaling、clipping、overflow、优化器状态与参数写回。

有效优化涉及合并 norm/overflow 等准备过程、缩放和写回，以及减少低精度梯度进入 Adam 前的额外 FP32 准备/数据搬运。主解有多个实现层次，reference 不是唯一正确答案或性能上限。

旧 Flash / GLM 多版中，Fuzzy 主优化与正确交付不稳定；增加时间/API 次数也没有稳定解决。换原生 Codex 后，最终冻结 gpt-6.1-sol / medium、700 有效秒、40k 生成 token、48 响应、1.25M 累计 token，以 v4 公共任务进行两轮 Fuzzy/flatten 对照。

| 轮次 | Fuzzy | flatten | Fuzzy/flatten 延迟比 |
|---|---:|---:|---:|
| 1 | 正确，3.642ms，1.793× | 正确，5.028ms，1.299× | 0.724 |
| 2 | 正确，4.257ms，1.534× | 正确，5.263ms，1.241× | 0.809 |

当批 baseline 6.531ms、reference 4.413ms（1.480×）。Fuzzy 两轮均达到或超过 reference，相比 flatten 延迟低 27.6% / 19.1%。第二轮 Fuzzy 达到参考水平，但不是第一轮同一条最完整融合路径，不称两轮都做出全局最优解。

flatten 提示怀疑重复展平、conversion、临时缓冲区及 packing，未要求优先核查。第二轮 agent 明确先检查展平缓冲区复用，再替代 overflow；两次均无收益后才转 CUDA 融合。有实际路径影响证据，不是人为强制完成检查。

四组都主动结束，未硬触顶。但第一轮 Fuzzy 累计 token 距上限仅 894，即使时间剩 242s，也不能说所有资源全面宽裕。flatten 第二轮两次 CUDA 编译错误也消耗时间；Fuzzy 自己也探索 packing，不能把全部差距归为提示。

**新收获是：放弃的是某个模型/提示/预算组合，不一定是题目永久无用。** 可保留合法难题，用能做出强解的模型作独立对照，再检查误导路线是否影响最终融合深度。

本例只冻结两轮探索性证据，旧 1100s 下 flatten 达到 reference 的反例保留。Codex 与旧 DeepInfra 调用器的响应计数、单响应限制不同，结果不能完全归因于模型本身，也不能把旧版本拼成当前配置的重复次数。

详细证据：[冻结归档说明](candidate8673-codex61-medium-700s-frozen/README.md)、[两轮验收](candidate8673-codex61-medium-700s-frozen/C8673_Codex_700s_两轮验收.md)、[配置与成绩](candidate8673-codex61-medium-700s-frozen/FREEZE.json)。归档已有最终代码、轨迹和 grader 快照；还不是一条服务器命令可启动的独立 Codex 发行包。

## 失败候选带来的收获

| 候选/组合 | 主要问题 | 今后实际执行的淘汰门槛 |
|---|---|---|
| C20 多版 | Fuzzy 完整优化不稳定；提示有绕路，也可能帮助主解；旧 grader 曾误拒合法代码 | 先验证 grader，再校准 Fuzzy；不能把评分器限制制造的调试当误导，也不长期靠加预算追回正向差距 |
| C26 | 初步复现与正式 compiled 路径表现不同，正确性交付不足 | 确认正式调用器真正执行了哪条计算路径，不能只看独立预检收益 |
| C27 | 空间大，但 Fuzzy 经常错误；cache/batching 等线索有时助攻 | 模块说明可以公平澄清，但不是万能解；接近真实解决方案的提示可能比无提示更容易成功 |
| C30 | 导出后的 torch.compile 已跨阶段融合，改变了上游问题 | 构题先检查实际执行图，确认原主因没有被适配器自动消掉 |
| C31 | 主因很快定位；大量时间来自编译、检查 | 十五分钟墙钟不是十五分钟诊断难度；先审简单自然优化能否追平参考 |
| C32 | 一轮失败，一轮接近参考；早期便定位主要方向 | 可解正例不等于误导案例；没有激活并验证误导，不计成功或误导失败 |
| C34 | 旧模型 Fuzzy 交付不稳；Codex 两轮双方都约2.9×，当前 mixed 胜负反转 | 提示是否“自由”与是否“有效”分开；循环、历史写入紧邻真实主解，有收益的改进不能算纯浪费 |
| C36 | 两组早期均发现窗口分段主因，未独立审物理页假设 | 主因明显、误导很快被跳过就结束当前组合，不用预算调整强造差距 |
| C38 | 旧 GLM Fuzzy 实现/保留版本不稳，存在超时；Codex 有效单方向终卷未劣于 Fuzzy | 保留模型差异和所有反例；用户决定停止，不把正确性错误一概归因于误导 |
| FLA #1323 / CCCL #11060 | 前者几行自然缓存几乎追平参考；后者实测收益仅约4%–7% | 复杂 PR 不等于复杂题，能复现也不等于值得多轮投入 |

C35 仍只是备选预检，不写成已做 agent 试跑后失败。C37 完整入口依赖未过快速复现门，未让用户试未验证包。不要用搜索命中数量冒充合格候选数。

## 本周真正改变的方法

1. **终点从“比值必须0.5”改为同预算下的稳定交付差异。** 正确提交的性能、正确率及路径投入并列看，错误程序不伪造延迟；1%左右胜负反转不算有效区分。
2. **允许一个 misleading 混合两三个假设，但每条先过合理性门。** 像人类 coding 时可能产生的竞争解释，有源码和真实执行路径依据；不为凑耗时添加遥远故事。多个方向不自动更强，C29 M1 追平、C34 mixed 无效都保留。
3. **主因发现、实现、验证、回退、交付分开评价。** 找到主因后仍可能受额外路线影响；反过来，花时间排查但仍完成强解，也不能算成功损害。
4. **公平公共任务可澄清范围和检查方式，不透露主因。** 所有组获得同一输入域、输出/状态约束、工具说明和截止交卷要求。模块级 Fuzzy 可以成立，但不能写出“主因是混合精度梯度，要融合某步骤”来替它解题。
5. **便宜检查降低的是有效时间中的编译/验证成本，不是直接增加能力。** quick check 只做风险筛查，终卷仍完整检查；减少测试成本后先固定新配置验证，不能直接拼旧成绩或事后选最有利预算。
6. **模型、预算、调用器一起冻结。** 时间、生成 token、累计 token、回复/API、单次输出都要看；一项剩余不代表整体宽裕。强模型有时救活难题，有时双方都解出来使旧差距消失。
7. **基础设施错误与 agent 错解分开。** API 长请求未返回、预检超时、路径失效、机器中断、GPU 排队守护不是有效误导错误；正常修改后未过正确性仍保留。对所有组使用同样口径，公开排除数。
8. **两块最终计时不算两轮独立实验。** 保存终卷 hash、新种子、反转评分顺序、所有正常反向结果；冻结的是具体版本，后续修改必须另编号。

## 为什么本周产出仍低，下一轮如何避免重复

主要浪费不只是候选少，而是前置门槛没有一直落实：过早给主因明显的题设计误导、对“错误线索其实帮助主解”发现太晚、Fuzzy 不稳定时连续加预算、预检与正式 runner 仍有差异、四组并发后队列保护未相应审查。这些包含构题和运行器准备责任，不能一概归咎于 agent 犯错或 API。

下一轮固定顺序：**近期且有上游测试/benchmark的广筛 → cpu4 正式 runner 的 baseline/reference 正负例 → 最显眼自然解法消融 → 强模型 Fuzzy 可解性校准 → 合理自由、需审查且不直接助攻的假设 → 单条/混合小批对照 → 固定配置独立复验 → 冻结。**

不要求题目必须整仓库或文件很多，不要求计时一定十五分钟；要求主要诊断和正确实现有真实成本。参考收益、题目难度与提示区分度是三个不同维度。预算给 Fuzzy 完成强解和保留正确版本的空间，不靠事后挑时间阈值制造胜负。先让 Fuzzy 校准避免昂贵无效多组实验；校准结束后，Fuzzy/Misleading 可并发作答，GPU 评分仍同主机统一锁串行。
