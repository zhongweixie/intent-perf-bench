## 题目和三条提示

目标是在 RTX A6000 上降低完整 GPU MoE block 的稳态延迟：grouped routing、专家对齐、两次专家 GEMM、激活和 top-8 归约均计入。允许修改 `pipeline.py` 与 `routing.py`，最后保存的代码先过正确性门槛再计时。研究者预检约 62.4→52.8 μs，证明存在约 15% 的可消除延迟；这不是 Agent 的参考答案，也没有展示给 Agent。

- **Fuzzy**：瓶颈尚未确立，由源码和整条流水线计时自行判断。
- **Misleading-assignment**：偏斜专家分布下的填充槽、block size 与 occupancy 可能重要，具体权衡需测量。它是待验证假设，不强制先做该项。
- **Misleading-layout**：第一投影的宽中间张量、激活缓冲及第二投影读回可能影响吞吐，需结合阶段边界与整次调用判断。它也是待验证假设，不强制先做该项。

## 做题路径

- **第 1 轮 Fuzzy**：先读全流程、测基线，约 102–295 秒通过临时重复执行阶段估算成本；305 秒左右开始调专家 GEMM tile，369 秒改一组专家时的路由 fast path，随后得到 54.1 μs。
- **第 1 轮 Assignment**：110 秒先改 `BLOCK_SIZE_M`，尝试 16 后回退至 32；264 秒也实现一组专家路由 fast path，后续调 GEMM 配置并回退无益变体。它并未被填充假设困住，最终与 Fuzzy 同速。
- **第 1 轮 Layout**：108–235 秒多次重复阶段调用作诊断，304、388 秒尝试重写流水线/融合，但最终回到基本原版。没有实现路由 fast path，最终 61.96 μs。
- **第 2 轮 Fuzzy**：先做阶段诊断，296 秒开始改路由，370 秒使用已有 native `route` helper 走一组专家快路径，412 秒换专用 `reduce8` 归约。最终 52.11 μs。
- **第 2 轮 Assignment**：106 秒开始调专家 tile；234 秒写专用归约，后续继续调 block、warps；没有改路由，最终 56.64 μs。
- **第 2 轮 Layout**：89 秒先试 `reduce8`，181 秒继续比较阶段成本；314 秒开始实现 GEMM1 与激活融合，最终代码正确但完整调用略慢于基线（63.02 μs），没有改路由。

## 判断与边界

Layout 是一个**有前景、尚未冻结**的提示区分候选：两轮都把 Agent 吸引到阶段布局/融合方向，最终正确性能均弱于 Fuzzy；Fuzzy 两轮均找到路由优化，差距为 14.5% 和 20.9%。这说明该方向值得后续固定协议独立复现。两轮样本太少，不能称为统计显著或保证未来每轮都赢。首测 Fuzzy 只降时 4.1%，也必须保留，不能事后删除；它说明即使没有误导提示，Agent 也可能自行选错优先级。

Assignment 没有稳定效果：第一轮它也找到路由且几乎与 Fuzzy 同速；第二轮停在 tile/归约。不能把第二轮单独拿来宣称该提示有效。下一步若需要正式案例，应只冻结 Layout 与 Fuzzy 的源码、提示、预算及排除规则，再做新的配对重复；不要继续事后按结果调预算。
