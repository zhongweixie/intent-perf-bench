## CUDA Case Studies

**文档**: [cuda_case_studies.md](cuda_case_studies.md)

### 内容概要

深度分析了 4 个 CUDA 性能回归测试案例，展示了 GPU 性能调试中的常见陷阱和反模式。

#### 案例列表

1. **ipb_cuda_001 - Huffman Decode**
   - 回归幅度: 18× (3.1ms → 56ms)
   - 根本原因: bit-by-bit O(n×k) 算法
   - 误导证据: "每线程重建解码表"（实际只建一次）
   - 修复方案: 10位LUT O(1)查表

2. **ipb_cuda_002 - ICP Correspondence**
   - 回归幅度: 14.12× (2.1ms → 29.4ms)
   - 根本原因: 400次 per-batch 同步（占92%时间）
   - 误导证据: 96.8% cache miss（算法固有特性）
   - 修复方案: 移除循环，单次启动所有点

3. **ipb_cuda_003 - NTT Butterfly**
   - 回归幅度: 6.4× (50ms → 320ms)
   - 根本原因: 7680次 per-row 同步（占96%时间）
   - 误导证据: twiddle factor 重计算（最多2×收益）
   - 修复方案: 2D grid 并行化 batch 维度

4. **ipb_cuda_004 - BLS12-381 MSM**
   - 回归幅度: 10.6× (59ms → 624ms)
   - 根本原因: 32次 per-window 同步（占95%时间）
   - 误导证据: 908MB memset 开销（占<4%时间）
   - 修复方案: 单次启动16384线程覆盖所有窗口

#### 核心发现

**共同反模式**: "进度监控回归" - 将 GPU 并行维度通过 CPU 循环串行化，并在每次迭代插入 `cudaDeviceSynchronize()`

**性能影响**:
- GPU 利用率崩溃: >80% → <5%
- 同步延迟累积: 数百次调用 = 数百毫秒开销
- 流水线破坏: 无法利用异步执行

**误导证据模式**:
- 量级不匹配的真实问题（cache miss、大内存操作）
- 不存在的问题（文档 vs 实际代码不符）
- 算法固有特性（非实现缺陷）

#### 关键学习点

1. **同步是隐形杀手**: `cudaDeviceSynchronize()` 在循环中累积成主导开销
2. **并行度是核心**: 串行化可并行维度导致数量级性能损失
3. **Profiler 数据需正确解读**: 显眼指标不一定是瓶颈
4. **代码审查不可或缺**: 必须验证性能分析文档的实际代码
5. **量化分析优先**: 计算各候选问题占比，优先解决 >50% 的主导瓶颈
