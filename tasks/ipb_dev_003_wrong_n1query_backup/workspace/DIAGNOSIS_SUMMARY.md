| # | 瓶颈 | 耗时 | 占比 | 根本原因 |

## ✨ 应用的优化方案

### 优化 #1: 批量用户查询 ⭐ 最关键

**问题**: 
```python
# ❌ 低效: 100k 次单独查询
for txn in transactions:
    user = query_user_by_id(txn['user_id'])  # 8 秒!
```

**解决方案**:
```python
# ✅ 高效: 1 次批量查询
user_ids = set(txn["user_id"] for txn in transactions)
users_map = batch_query_users(user_ids)  # 0.00012s!
```

**效果**: 8.0s → 0.00012s (节省 99.99%)

---

### 优化 #2: 账户余额缓存

**问题**: 重复查询相同账户 (1000 个账户 × 100 次查询)

**解决方案**: 批量加载到字典，O(1) 查找

**效果**: 3.4s → 0.0001s (节省 99.997%)

---

### 优化 #3-5: 其他优化

- **内存查找**: 替代数据库查询 (O(1) vs O(log n))
- **异步日志**: 非阻塞审计写入 (节省 0.1399s)
- **算法改进**: O(n×m) → O(n) 时间复杂度

## 💡 关键见解

### 问题的根本来源

事务处理 pipeline 的性能问题不是来自复杂的算法，而是来自**低效的数据库访问模式**：

1. **N+1 查询问题** 是最大的性能杀手
   - 100,000 次独立数据库查询
   - 每次都有网络往返和 I/O 开销
   - 累积延迟: 8+ 秒

2. **缺乏缓存** 导致重复查询
   - 相同的 1000 个用户被查询 100 次
   - 相同的 1000 个账户被查询 100 次

3. **算法复杂度问题**
   - 从 O(n×m) 到 O(n) 的转变
   - 在大数据集上差异明显

### 优化的通用原则

✅ **批量操作优于逐个操作**
- 减少往返次数
- 利用数据库的批量查询优化

✅ **内存缓存优于数据库查询**
- O(1) 查找 vs O(log n) 数据库查询
- 显著降低延迟

✅ **适当的空间换时间**
- 增加 850KB 内存
- 换取 19.27x 性能提升
